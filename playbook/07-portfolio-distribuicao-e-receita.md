# Capítulo 7 — Portfólio, distribuição e receita

> Construir é 30% do trabalho. Distribuir é 70%. O portfólio é a prova que abre a distribuição.

---

## Por que portfólio público importa em 2026

No mercado de IA aplicada, claims sem evidência valem zero.

Todo mundo diz que usa IA. Todo mundo diz que automatizou. Todo mundo diz que tem sistema.

O que diferencia quem está de fato operando:

**Repositórios públicos com histórico de commits real.**

O commit não mente. A data não mente. O diff não mente.

Isso é o que este projeto pratica: o repositório `modo-operador` é ele mesmo a prova do método. Cada capítulo escrito por Jules, cada decisão no Decision Ledger, cada PR aberto por agente — tudo auditável.

---

## Como construir um portfólio técnico sem saber programar

Você não precisa escrever código para ter um portfólio técnico.

Você precisa de **artefatos verificáveis**:

1. **Repositórios públicos** com projetos reais — mesmo que o código tenha sido escrito por Jules
2. **Decision Ledger** documentando escolhas de arquitetura
3. **Issues e PRs** com discussão real de problema → solução
4. **README honesto** que descreve o que é e o que não é
5. **Commits semânticos** com mensagens que contam a história

Qualquer pessoa pode ver o histórico e entender o que foi construído, como e quando.

## A estratégia de distribuição em três camadas

### Camada 1 — Prova (repositório público)
Tudo que você constrói tem um repositório público correspondente.

O repositório serve como:
- Prova de execução
- Material de conteúdo (cada commit é um post em potencial)
- Credencial técnica
- Ponto de entrada para quem descobre seu trabalho

### Camada 2 — Conteúdo (redes sociais + newsletter)
O repositório alimenta o conteúdo. Cada capítulo escrito, cada automação funcionando, cada proof publicado — vira conteúdo.

Fluxo:
```
Repositório → extrai insights → formata por canal → publica
```

- **Twitter/X:** threads com os pontos mais táticos de cada capítulo
- **Instagram:** carrosséis com comparações visuais (ciclo 2024 vs 2026)
- **Newsletter:** versão longa, mais contexto, link para o produto
- **YouTube/Shorts:** demonstração ao vivo das ferramentas

### Camada 3 — Oferta (produto pago)
A audiência construída com conteúdo é convertida para produto.

Modelo de conversão:
```
Conteúdo gratuito (repositório + posts)
→ Waitlist (landing page)
→ Early access com desconto
→ Produto completo
→ Comunidade / nível seguinte
```

## Plataformas de venda para produto digital

### Mercado brasileiro
- **Cakto** — mais simples, zero mensalidade, comissão na venda
- **Hotmart** — mais features, mais complexo, mais credibilidade no mercado BR
- **Gumroad** — funciona para mercado BR se tiver audiência internacional também

### Mercado internacional
- **Gumroad** — produto simples, setup em minutos
- **Lemon Squeezy** — melhor para SaaS e licenças de software
- **Stripe** — direto, você controla tudo, precisa construir o checkout

## Como precificar produto de IA operacional

Regra geral: **preço pelo resultado, não pelo volume de conteúdo**.

Quem compra este playbook não está comprando X horas de vídeo ou Y páginas de texto. Está comprando:
- O sistema que funciona
- O tempo economizado aprendendo do zero
- A vantagem de quem já testou e filtrou o que funciona

**Faixa de preço BR para produto de IA aplicada:**
- Entry level (intro, ebook curto): R$ 47–97
- Playbook completo com ferramentas: R$ 197–397
- Comunidade + produto + acesso ao autor: R$ 497–997/mês

**Para mercado internacional:** multiplique por 3–5x. O mercado inglês paga mais por conteúdo técnico aplicado.

## A sequência correta de lançamento

Erro comum: lançar antes de ter prova.

Sequência correta:

```
1. Constrói o que vai vender (de verdade, não promete)
2. Documenta com evidência (repositório, screenshots, logs)
3. Publica a prova (posts, repositório público)
4. Abre waitlist (landing page)
5. Aquece a lista (conteúdo gratuito baseado no produto)
6. Lança para a lista primeiro (early access, desconto)
7. Abre para o público
8. Itera com base no feedback real
```

Cada etapa depende da anterior. Não pule.

## O papel do Benni Control Plane no ciclo de receita

O BCP não é só controle de código. É o sistema de rastreabilidade do negócio:

- **Decision Ledger** — cada decisão de produto é registrada. Você sabe por que tomou cada escolha e quando.
- **Snapshots** — estado do projeto em cada momento relevante. Fácil de voltar e entender o contexto.
- **Artifacts** — produtos, landing pages, outlines — tudo linkado ao projeto.
- **Run plans** — sequência de execução documentada antes de agir.

Isso cria uma trilha auditável do produto ao longo do tempo — útil para você, para eventuais parceiros e para provar que o método funciona.

## Resumo operacional

- Portfólio = repositório público com histórico real, não apresentação de slides
- Distribuição em 3 camadas: prova → conteúdo → oferta
- Conteúdo alimentado pelo repositório (cada commit é um post em potencial)
- Plataforma BR: Cakto (simples) ou Hotmart (mais features)
- Preço pelo resultado, não pelo volume
- Sequência: constrói → documenta → prova → waitlist → lança
- BCP é o sistema de rastreabilidade do negócio, não só do código
